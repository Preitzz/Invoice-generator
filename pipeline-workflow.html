Section 0

Standing orders

RULE 1

One change open at a time

No second proposal until the current one is archived. Parallel changes make the delta model meaningless.

RULE 2

Ambiguity stops the line

An agent that guesses has produced a defect. Unresolved questions go in the register, never into generated code.

RULE 3

Scope lock

The diff touches only files named in tasks.md. Everything else is rejected at review.

RULE 4

Specs change by archive only

Never hand-edit openspec/specs/. It fills in as changes are synced and archived.

00
Phase 00

Environment setup

OWNER Whole teamPRODUCES openspec/ scaffoldingONCE PER PROJECT

Node 20.19+ required. Install the CLI, scaffold the repo, then widen the workflow profile so you get artifact-by-artifact control.

npm install -g @fission-ai/openspec@latest cd your-capstone openspec init --tools claude,cursor,opencode openspec config profile # add: continue, verify openspec update
Caution — Windows Install Node, the CLI and your agent all inside WSL, and keep the repo in the Linux filesystem. A Windows CLI driving a WSL agent is the most common setup failure. Set git config core.autocrlf input before any spec is generated.
01
Phase 01

Crude prompt → Level 1 spec

OWNER TeamPRODUCES docs/01-spec-L1.mdNOT AN OPENSPEC STEP

Write docs/00-crude-prompt.md in ten minutes, unedited. Then have the agent expand it into a behavioural spec — in ordinary chat, not through OpenSpec.

The generation prompt must state: one SHALL per requirement, one scenario per requirement, no invented requirements, no architecture, and every ambiguity logged rather than resolved.

Artifact sections Purpose · Actors · Domain objects with lifecycle states · Requirements (SHALL + Given/When/Then) · Invariants · Out of scope · Open questions · Assumptions the generator made
Why not OpenSpec here OpenSpec generates artifacts from a scoped request. Feed it a whole product idea and you get one bloated change folder, which defeats delta tracking entirely.
G1
Hold point G1 — inspection required

Level 1 spec review

One named reviewer. Not the team. Committees do not catch ambiguity. All ten items must pass; a failure returns a specific edit instruction, never “make it better”.

Phase 02

Slice the spec

OWNER Team + agentPRODUCES a slice tableNO FILES WRITTEN

First make the spec ambient. Add to openspec/config.yaml a context: block naming docs/01-spec-L1.md as authoritative, plus your stack and conventions. Every later proposal inherits it.

/opsx:explore

Ask for the smallest set of independently shippable changes, each with a kebab-case name, the requirement IDs it covers, and its dependencies. Explicitly forbid writing files.

Calibration A capstone should yield 4–8 slices. Fifteen means your slices are too fine. Two means too coarse. Re-slice before proceeding — re-slicing later means discarding generated work.
03
Phase 03

Generate change artifacts

OWNER Slice ownerPRODUCES openspec/changes/<slice>/ONE SLICE ONLY

For the first two slices, generate artifacts one at a time so each is approved before the next is built on top of it.

/opsx:new-change room-inventory /opsx:continue

Once the team trusts the output, later slices can use the single-pass form:

/opsx:propose availability-query
Change folder contents proposal.md why and what changes · specs/ delta requirements and scenarios · design.md technical approach · tasks.md implementation checklist

G3
Hold point G3 — automated

Structural validation

Machine check. Cheap, fast, and far narrower than people assume.

openspec validate --strict
What this does not do It checks structure only — required sections present, format valid, cross-artifact dependencies aligned. It does not check behavioural correctness and it does not run tests. Given/When/Then scenarios are supported but unenforced. A change can pass here and be entirely wrong. G2 is not optional because G3 exists.

ReleasedG3 ·
04
Phase 04

Implement

OWNER Slice ownerBRANCH change/<slice>PRODUCES code + tests
/opsx:apply

Then, before reading the diff, run the agent's own review pass. Treat it as a first reader, not a gate — the docs are explicit that it will not catch everything.

/opsx:verify npm test && npm run lint openspec validate --strict git commit -am "feat(room-inventory): implement REQ-001..003"
Definition of done All tasks checked · every scenario has an automated test · tests and lint pass · validation passes · no TODO, no placeholder, no commented-out code · no file touched outside tasks.md
05
Phase 05

Sync and archive

OWNER Slice ownerPRODUCES openspec/specs/ + archive/AFTER MERGE TO MAIN
/opsx:sync /opsx:archive

Sync merges the change's delta specs into openspec/specs/. Archive files the completed change under openspec/archive/ with a date prefix.

Why specs/ starts empty It is meant to. The living specification accumulates one archived change at a time. A near-empty specs/ in week one is correct, not a gap to fill.
06
Phase 06

Return to Phase 03 — or close out

LOOP Once per sliceNEVER BATCH

Each remaining slice repeats Phase 03 → G2 → G3 → Phase 04 → Phase 05. When the last slice is archived, the deliverables are:

#ArtifactWhat it proves
1docs/00-crude-prompt.mdThe unedited starting point
2docs/01-spec-L1.mdWhat the team agreed to build
3openspec/specs/The living specification
4openspec/archive/Why each decision was made
5src/ + testsBehaviour traceable to scenarios
The real deliverable Item 4. Anyone can show working code. The archive shows why it was built that way — which is the thing a capstone is actually assessing.

Controlled language for specs

Adapted from ASD-STE100 Simplified Technical English — the 1986 aircraft maintenance writing standard built so an instruction cannot be read two ways. Ambiguous specs produce ambiguous code; fix it at the source.

One instruction per sentence. 20 words maximum.
Active voice. Name the actor.
One word, one meaning, project-wide. No synonyms.
No noun cluster longer than three words.
Every requirement states its failure behaviour.
No unquantified comparative. “Fast” → “under 300 ms at p95”.
Warnings appear before the step, never after.
Banned — no testable meaning
robustseamlessscalableperformant user-friendlyintuitivebest-practiceleverage appropriateproperlygracefullyas needed where relevanthandlesupportand/or

Anti-slop review card

Run on every pull request. Print it.

  • Every scenario has a test that fails if the behaviour breaks
  • No banned word in any markdown or code comment
  • Every number in the code traces to a number in a requirement
  • No dependency added without justification in the PR
  • No file touched outside tasks.md
  • Error paths implemented, not only happy paths
  • No TODO, placeholder, or commented-out block
  • Comments explain why, never what
  • Someone who didn't write it can explain it from the diff alone
